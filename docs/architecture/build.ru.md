# Сборка и запуск игры

[English version](build.md)

Шаг 9 MVP: игра, которая работает без редактора. Редактор собирает папку,
которую игрок копирует и запускает: программу-проигрыватель, модуль игры,
библиотеку движка и один пакет ресурсов.

Пометки статуса: см. [README](README.ru.md).

## Решения [planned, step 9]

Устройство - устоявшееся для выпуска игры из редактора: ресурсы
готовятся в форматы для игры через кэш импорта, упаковываются в один
архив с доступом по ID и запускаются готовой программой-проигрывателем
под каждую платформу; нового здесь ничего нет.

- **Проигрыватель** (`apps/player`, `yqlora-player`): библиотека движка в
  режиме игры (`ApplicationMode::Game`), без редактора, ImGui и
  компилятора шейдеров. Он собирается вместе с движком под каждую
  платформу движка и поставляется с редактором, поэтому сборка игры его
  копирует, переименовав в игру, а не компилирует. Та же программа с
  `--project <папка>` запускает проект из исходных файлов, чтобы проверить
  сборку без упаковки.
- **Модуль игры компилируется под каждую платформу**, куда игра выходит,
  как любой код C++: редактор собирает под платформу, на которой работает,
  а игра под другую платформу собирается на ней (или в её CI). Раздел Build
  перечисляет целевые платформы; цель, которую здесь не собрать, так и
  сказано.
- **Подготовка и кэш импорта**: каждый ресурс один раз переводится в свой
  вид для игры, и результат хранится в кэше проекта (`.build/cache/`, по
  хэшу исходного файла, его настроек импорта и версии подготовки).
  Редактор тоже грузит из кэша, поэтому большая модель или текстура
  переводится один раз, а не при каждом запуске, и сборка берёт те же
  результаты. Изменился исходник или настройка - подготовка заново. Виды
  для игры:
  - сцены и префабы: двоичный вид того же дерева (с версией, как у JSON,
    который остаётся исходником для редактора и системы контроля версий);
  - модели и меши: `ModelData` и `MeshData` как в памяти, поэтому
    проигрыватель никогда не разбирает glTF;
  - текстуры: с цепочкой мипов, сжатые для видеокарты (BC7 для цвета, BC5
    для карт нормалей, BC4 для одного канала; RGBA8, где устройство этих
    форматов не знает), поэтому видеопамять текстур уменьшается примерно
    вчетверо;
  - шейдеры: SPIR-V с отражением и раскладкой материала, поэтому
    проигрывателю не нужен glslang (SPIRV-Cross остаётся в бэкенде OpenGL);
  - материалы, физические материалы, темы, шрифты: их данные как есть.
- **Пакет** (`<игра>.ypak`): оглавление по `ResourceId` (смещение, размер,
  вид, сжатие zstd для каждой записи) и сами записи, читаются через
  отображение в память. ID зашиты, поэтому проигрывателю не нужны ни
  `.meta`, ни пути; таблица путей хранится только для сообщений.
- **Что входит**: всё, до чего можно дойти от сцен сборки (ссылки свойств,
  вложенные префабы, материалы, текстуры) и от глобальных узлов, плюс
  папки с пометкой "Всегда включать" для ресурсов, которые скрипт ищет по
  имени. Ресурс, которого нет в пакете, - ошибка сборки, а не игры во время
  работы.
- **`ResourceSource`**: `ResourceCache` читает через источник: файлы проекта
  с кэшем импорта в редакторе и при запуске с `--project`, пакет в
  собранной игре. Загрузчики и всё, что над ними, не меняются.
- **Смена сцен**: `scenes().load(scene)` из скрипта меняет сцену между
  кадрами, никогда посреди обновления (старая сцена останавливается, новая
  начинает со следующего кадра). `scenes().loadAsync(scene)` читает её
  ресурсы в рабочем потоке и сообщает прогресс, поэтому экран загрузки
  может двигаться; загрузчики - функции своего входа и работают в любом
  потоке, а кэш публикует их результаты в главном.
- **Глобальные узлы**: префабы из списка в настройках проекта (General)
  создаются один раз при запуске игры и живут при смене сцен - для
  менеджера игры, музыки и меню паузы.
- **Сохранения игры**: `saveData().write(slot, value)` и `read(slot)` с
  записью или JSON, пишутся атомарно в папку данных пользователя платформы
  (`%APPDATA%`, `~/.local/share`); редактор и Play используют папку в кэше
  проекта, поэтому тесты игры никогда не трогают сохранения выпущенной.
- **Экран**: раздел Display (разрешение, режим окна: в окне, без рамки на
  весь экран, исключительный полноэкранный, изменяемый размер, vsync из
  Graphics) - значение по умолчанию; выбор игрока в меню настроек игры
  задаётся через `display()` и хранится в папке данных пользователя.
- **Собранная папка**: проигрыватель, переименованный в игру, модуль игры,
  библиотека движка, SDL, пакет, `licenses.txt` (движок и его библиотеки)
  и, на Windows, значок игры в исполняемом файле. Лог пишется в файл в
  папке данных пользователя; при падении видно, где он.

## Где кончается движок и начинается игра

Движок собирает, упаковывает, загружает, меняет сцены, хранит сохранения
и применяет настройки экрана. Игра решает, какие сцены есть и когда их
менять, что лежит в сохранении и когда оно пишется, что предлагает её меню
настроек.

## Фазы (коммит на фазу)

### B.1 Проигрыватель

- `apps/player` в режиме игры, запуск с `--project`, раздел Display и
  `display()`, лог в файл, сообщение о падении.
- Тесты: проигрыватель запускает папку проекта, проходит десять кадров без
  окна и выходит с кодом 0; проект без стартовой сцены сообщает об этом и
  выходит с кодом ошибки; настройки экрана игрока перекрывают проектные.

### B.2 Сцены, глобальные узлы, сохранения

- `SceneRequests` с `load`, глобальные узлы, `saveData()`.
- Тесты: смена сцены, запрошенная в `onUpdate`, происходит после кадра,
  каждый компонент старой сцены получает `onStop`; глобальный узел
  переживает две смены; сохранение пишется и читается обратно; прерванная
  запись оставляет старое сохранение.

### B.3 Подготовка и кэш импорта

- Подготовка для каждого вида, кэш по хэшам, двоичный вид сцен, сжатие
  текстур с мипами, SPIR-V с отражением; редактор грузит через кэш.
- Тесты: вторая загрузка модели читает кэш, а не glTF; изменённая
  настройка импорта готовит заново; двоичная сцена после загрузки равна
  JSON; сжатая текстура держит цвет в пределах ошибки формата;
  подготовленный шейдер рисует тот же кадр, что скомпилированный.

### B.4 Пакет

- Запись и чтение `.ypak`, обход зависимостей, "Всегда включать",
  `ResourceSource` для файлов и для пакета.
- Тесты: собранный пакет держит ровно достижимые ресурсы; ресурс, на
  который ссылается только глобальный узел, включён; недостающий
  проваливает сборку со своим именем; сцена грузится из пакета без папки
  проекта.

### B.5 Сборка из редактора

- Раздел Build (целевые платформы, сцены сборки, папка вывода, отладка
  или выпуск), модуль игры в выпуске, "Собрать" и "Собрать и запустить" с
  прогрессом, логом и отменой.
- Тесты (логика без интерфейса): в папке вывода ожидаемые файлы; вторая
  сборка без изменений берёт кэш; проваленная сборка модуля
  останавливается с ошибками компилятора в логе.

### B.6 Загрузка в фоне

- `loadAsync`, загрузчики в рабочих потоках, прогресс.
- Тесты: сцена с 50 текстурами грузится, пока кадры идут; прогресс идёт
  от 0 до 1; уход во время загрузки её отменяет без утечек (asan).

пакет), проект (папка кэша), настройки проекта (Display, Build), скрипты
