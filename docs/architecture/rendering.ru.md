# Рендер

[English version](rendering.md)

Камеры, виды и как сцена попадает в рендерер. Стадии кадра рендера - в
[пайплайне кадра](frame.ru.md).

Пометки статуса: см. [README](README.ru.md).

## Пайплайн рендера

Как кадр доходит от сцены до экрана. Рендерер читает только снимок, сделанный
на стадии Extract, и никогда не читает сцену.

### Сейчас [done]

```
 СЦЕНА (просчитана, мировые матрицы готовы)
   RenderSystem: активные камеры по order
   MeshRenderer: включённые компоненты, их меш (из ResourceCache), цвет,
                 слой узла
   Node3D: мировые матрицы
        |
        |  extractFrame(scene, aspect)                    render/FrameBuilder
        v
 FrameData (снимок, ничего не указывает обратно в сцену)
   views[]      по одному на камеру: вид и проекция, очистка,
                фон, маска слоёв
   drawItems[]  меш с его ID и ревизией, мировая матрица, цвет, слой,
                ID узла
   editor       сетка вкл/выкл, выделенные узлы       (только редактор)
        |
        |  Renderer::render(frame)          -> задний буфер окна
        |  Renderer::render(frame, target)  -> RenderTarget (текстура)
        v
 OpenGLRenderer::drawScene                           backends/opengl
   для каждого вида, в порядке камер:
     очистка      цвет и глубина / только глубина / ничего
     MeshPass     элементы, чей слой есть в маске вида, через камеру
                  вида, один постоянный направленный свет
   GridPass       только редактор, поверх последнего вида
   OutlinePass    только редактор, контур выделенных узлов
        |
        v
 UiRenderer (ImGui), затем present (смена буферов)
```

- **Игра** (`Application` в режиме игры) делает это раз в кадр на стадиях
  `extract` и `render` цикла `FrameLoop` (см. [кадр](frame.ru.md)), в окно.
- **Редактор** на этих стадиях своей сцены не рисует. Каждое окно сцены
  (Сцена, Игра, превью камеры) само вызывает `extractFrame` со своим
  соотношением сторон и рисует в свой `RenderTarget` на стадии интерфейса;
  ImGui потом показывает текстуру. Окно сцены добавляет вид камеры редактора
  и наложение (сетка, контур).

### Со слоем над графическим API [planned, RHI]

```
 Extract   -> FrameData (ещё свет, материалы)
 Prepare   -> для каждого вида: отсечение по границам и маске слоёв,
              сортировка (непрозрачное спереди назад, прозрачное сзади вперёд)
 Graph     -> проходы объявляют, что читают и пишут, граф их упорядочивает:
              тени -> непрозрачное -> небо -> прозрачное -> постобработка -> HUD
              (+ проходы, которые редактор добавляет своим видам: сетка, контур)
 Renderer  -> записывает проходы командами RHI         engine/render
 RHI       -> один интерфейс над OpenGL, Vulkan, D3D12  backends/<api>
 Present
```

## Этап RHI [planned, RHI]

Делается до шага 5, чтобы шейдеры, материалы и свет писались один раз для
всех графических API. Сейчас делается только реализация на OpenGL; Vulkan и
D3D12 позже. В интерфейсе нет допущений OpenGL, но есть только то, что
нужно рендереру сегодня: ничего не добавляется "для Vulkan" раньше самого
Vulkan.

### Где проходит граница

| Движок (`engine/render`) | Бэкенд (`backends/<api>`) |
| --- | --- |
| `Renderer`, проходы (`MeshPass`), Prepare, граф проходов | `rhi::Device`, `rhi::CommandList` своего API |
| копии ресурсов в видеопамяти по ID и ревизии (`GpuResourceCache`) | буферы, текстуры, сэмплеры, конвейеры своего API |
| шейдеры: компиляция GLSL в SPIR-V, отражение | шейдерный модуль своего API из SPIR-V |
| что рисовать и в каком порядке | исполнение команд |

- RHI ничего не знает о графе. Граф строится поверх RHI и превращается в
  его команды, поэтому каждый проверяется без другого.
- ImGui - отдельная интеграция бэкенда (`UiRenderer`), а не часть RHI:
  рисует через тот же API и устройство, но RHI от неё не зависит. Текстура
  ресурса для ImGui (`uiTexture`) идёт через эту интеграцию.
- Рендер создаётся через `createDevice(api)` вместо `createRenderer(api)`;
  классов рендерера по API больше нет.

### Контракты

- **Время жизни объектов в видеопамяти.** Объекты RHI - абстрактные классы
  в `unique_ptr`, владеет тот, кто создал. Удаление объекта не освобождает
  его сразу: устройство освобождает его, когда закончены кадры, которые
  могут им пользоваться (в OpenGL сразу, в Vulkan и D3D12 после кадров в
  полёте). Команды ссылаются на объекты по указателю, действительному до
  конца кадра. Копии ресурсов в видеопамяти живут по ID ресурса и ревизии
  (`GpuResourceCache`), никогда по адресу данных в памяти: новая ревизия
  заменяет копию, старая освобождается по тому же правилу.
- **Состояния ресурсов.** Текстура в каждый момент в одном состоянии: цель
  цвета, цель глубины, чтение в шейдере, показ на экране. Смена - явная
  команда (`transition`), граф вставляет их между проходами. OpenGL их
  пропускает, Vulkan и D3D12 превращают в барьеры. Пока только эти четыре
  состояния.
- **Конвейеры** неизменяемы после создания: шейдеры, раскладка вершин, тест
  и запись глубины, отсечение граней, смешивание, форматы целей, число
  образцов. Конвейер рисует только в цель тех же форматов и числа образцов;
  несовпадение - ошибка (проверяют тестовый RHI и отладочная сборка).
- **Данные шейдеров** идут uniform-блоками по частотам: кадр (время, свет),
  вид (камера), материал (шаг 5), объект (матрицы). Раскладка std140;
  структуры C++ повторяют её явными `alignas` и при загрузке шейдера
  сверяются с отражением (размер и смещение каждого поля), а не считаются
  совпадающими на веру. Данные объектов лежат в одном буфере на кадр и
  привязываются со смещением, выровненным по ограничению устройства
  (`GL_UNIFORM_BUFFER_OFFSET_ALIGNMENT` в OpenGL).
- **Одно соглашение о clip space** во всём движке: правосторонний мир,
  глубина в clip space от 0 (ближняя) до 1 (дальняя), y в NDC вверх, строки
  текстур сверху. Проекции строятся только так (`math::perspective`),
  поэтому камеры не знают API; `DepthRange` больше нет. Подстраивается бэкенд: OpenGL
  получает вершинные шейдеры от SPIRV-Cross с глубиной, переведённой в
  -1..1 (`fixup_clipspace`), Vulkan будет переворачивать y через viewport.
  Переворот целей рендера по вертикали в OpenGL остаётся внутри бэкенда
  (углы `UiTexture`).
- **Потеря устройства**: путь смены графического API без перезапуска (см.
  ниже) восстанавливает и после потери устройства в Vulkan и D3D12. OpenGL
  устройство не теряет, поэтому сейчас ничего не добавляется.

### Шейдеры

Пишутся один раз на GLSL 450 в стиле Vulkan (`set`, `binding`) и
компилируются glslang в SPIR-V. SPIR-V - промежуточная форма: OpenGL
получает GLSL 330 от SPIRV-Cross, Vulkan будет брать SPIR-V как есть, D3D12
HLSL от SPIRV-Cross. Переносимость не автоматическая: порождённый код и
профиль ниже проверяются на каждом целевом API, когда появится его бэкенд.

- **Профиль шейдеров** - то, что умеют все целевые API; шейдер вне профиля
  отклоняется при компиляции с сообщением:
  - стадии: только вершинная и фрагментная;
  - ресурсы: uniform-блоки std140 и совмещённые сэмплеры (`sampler2D`,
    `samplerCube`); без storage-буферов, image и отдельных сэмплеров;
  - наборы: 0 кадр, 1 вид, 2 материал, 3 объект;
  - входы вершин по постоянным location: 0 позиция, 1 нормаль, 2 `uv0`
    (касательные с картами нормалей в шаге 5);
  - ограничения OpenGL 3.3: не больше 16 текстур на шейдер, uniform-блок не
    больше 16 КБ.

  У профиля есть версия; файл шейдера в шаге 5 записывает её в свой
  `.meta`, новая версия профиля - миграция (см.
  [форматы проекта](project.ru.md)).
- **Отражение даёт строение, а не представление.** `ShaderReflection`
  читает из SPIR-V uniform-блоки, имена полей, типы, смещения и размеры,
  наборы и привязки, текстуры. Как поле показывается в инспекторе
  материала (ползунок 0..1 для `roughness`, выбор цвета для `baseColor`,
  подпись, группа), берётся из пометок рядом с полем в том же файле шейдера
  и ложится на атрибуты свойств из [отражения](reflection.ru.md). Типы и
  привязки никогда не пишутся дважды; синтаксис пометок выбирается в шаге 5.
- **Компиляция**: `#include` (относительно файла и из библиотеки шейдеров
  движка), defines и параметры компиляции, ошибки с исходным файлом и
  строкой, кэш результатов в памяти по исходнику, включаемым файлам и
  defines на время запуска.
- **Устройство принимает SPIR-V**, а не исходник GLSL. Компилятор (glslang) -
  отдельная часть, которой пользуются редактор и движок при запуске; игра,
  собранная без редактора, может везти заранее скомпилированные шейдеры и
  работать без glslang (шаг 9). SPIRV-Cross остаётся в бэкенде OpenGL.
- **В отражение попадает только то, чем стадия пользуется**: подключённый,
  но не прочитанный блок не ресурс шейдера, и задавать его перед
  отрисовкой не нужно. Поэтому шейдер может подключить всю библиотеку
  движка (`<yqlora/uniforms.glsl>`) и оставить только то, что читает.
- **Встроенные шейдеры** **[done]** лежат в `engine/shaders` и вшиваются в
  библиотеку движка. Их путь в компиляторе начинается с `engine:`
  (`engine:mesh.vert`), ошибки показывают его же. `#include <yqlora/...>`
  берёт файл из `engine/shaders/include`, так что шейдеры проекта в шаге 5
  подключают ту же библиотеку.
- **Где живёт** **[done]**: `engine/internal/yqlora/shader` -
  `ShaderCompiler` (glslang, include, defines, кэш), `reflectShader` и
  `checkShaderProfile`, `UniformLayout` с `checkUniformLayout` (сторона
  блока в C++: `YQLORA_UNIFORM_MEMBER` даёт имя, смещение и размер поля),
  `buildShader` (весь путь, ошибки всех шагов вместе). В бэкенде OpenGL -
  `GlslTranslator`: SPIR-V в GLSL 330 с переименованием ресурсов и
  переменных между стадиями, чтобы GLSL 330 находил их по имени.

### Prepare и граф проходов

- **Prepare** работает по видам: один объект может быть виден в окне Игра и
  не виден в окне Сцена. Отсечение по границам меша (AABB, их несёт
  `DrawItem`) пирамидой видимости и по маске слоёв; непрозрачное
  сортируется спереди назад с группировкой по конвейеру и материалу,
  прозрачное сзади вперёд относительно этого вида.
- **Граф в объёме MVP**: проход объявляет текстуры, которые читает и пишет;
  граф находит зависимости, упорядочивает проходы, создаёт и освобождает
  временные текстуры (маску контура) в пределах кадра, вставляет смены
  состояний и сообщает о цикле или о чтении текстуры, которую никто не
  писал. Не сейчас: совмещение памяти, асинхронные очереди, параллельная
  запись команд, автоматический разбор барьеров сверх четырёх состояний.
  Они придут с Vulkan и D3D12, когда понадобятся.
- **Проходы редактора**: вид принимает от владельца список дополнительных
  проходов. Окно сцены добавляет в свой вид сетку и контур выделения;
  проходы живут в редакторе и держат свои данные (выбранные узлы, цвет),
  движок их только исполняет. `FrameData::editor` уходит, движок ничего не
  знает о редакторе.

### Фазы (коммит на фазу)

1. **R.1 RHI и OpenGL** **[done]**. `rhi::Device`, `rhi::CommandList`, буферы,
   текстуры, сэмплеры, конвейеры, цели рендера, состояния ресурсов, правило
   времени жизни. Реализация на OpenGL: `GlMesh`, `GlTexture`,
   `GlRenderTarget` становятся объектами RHI, старые проходы работают
   поверх них. Минимальный тестовый RHI, который записывает команды и
   проверяет совместимость конвейера и цели, с первой фазы: ошибки
   интерфейса найдутся раньше, чем их закрепит реализация на OpenGL.
2. **R.2 Шейдеры** **[done]**. glslang и SPIRV-Cross, профиль, `ShaderReflection`,
   include, defines, ошибки с файлом и строкой, кэш в памяти, сверка
   структур std140 с отражением; встроенные шейдеры на GLSL 450;
   соглашение о clip space, `DepthRange` уходит из камер.
3. **R.3 Рендерер в движке.** `Renderer` - класс движка поверх
   `rhi::Device`, `MeshPass` и `GpuResourceCache` переезжают в
   `engine/render`, `createDevice(api)`, ImGui отдельной интеграцией
   бэкенда. Редактор и `Application` меняются только там, где создают
   рендерер.
4. **R.4 Prepare и граф.** Отсечение, сортировка, границы в `DrawItem`, граф
   в объёме MVP, проходы сетки и контура в редакторе, `FrameData::editor`
   убран.
5. **R.5 Тесты и документы.** Тесты на тестовом RHI: порядок проходов и
   зависимости графа, отсечение, сортировка, отсутствие лишних draw,
   текстуры каждого прохода. Небольшие интеграционные тесты OpenGL (буферы,
   текстуры, конвейеры, кадр в цель), которые идут там, где можно создать
   контекст OpenGL, и пропускаются иначе. Пометки `[planned, RHI]` в этом
   файле и в [кадре](frame.ru.md) снимаются.

Вне этапа: бэкенды Vulkan и D3D12, поток рендера, тени, небо и
постобработка (место в графе для них готово).

## Меши и текстуры [done]

- **Вершина** (`Vertex`): положение, нормаль, `uv0`. `uv0 = (0, 0)` - левый
  верхний угол картинки, как в glTF; касательные придут с картами нормалей
  в шаге 5.
- **Меш** (`MeshData`): вершины, индексы треугольников против часовой
  стрелки снаружи, подмеши и границы (AABB). Подмеш - диапазон индексов со
  своим материалом; его индекс - слот материала у `MeshRenderer` (шаг 5),
  и он помнит индекс материала исходного файла. Границы ускоряют выбор
  мышью, позже - отсечение.
- **Текстура** (`TextureData`): RGBA по байту на канал, строки сверху вниз,
  и как её читать: sRGB или Linear, фильтр, повтор, мипмапы (настройки
  импорта). На меши текстуры ложатся через материалы, шаг 5.
- **Копии в видеопамяти** бэкенд держит сам, по ID ресурса и ревизии
  (`GpuResourceCache`): `DrawItem` несёт меш с его ID и ревизией, копия
  другой ревизии заменяется, а копия, которой не рисовали 120 кадров,
  освобождается. Шаблон один для всех бэкендов и видов ресурсов.
- **Текстура в интерфейсе**: `Renderer::uiTexture` даёт текстуру ресурса
  для ImGui (превью в инспекторе), с цветами как в файле, без перевода из
  sRGB: ImGui рисует в обычный буфер, и переведённая картинка была бы
  темнее.

## Камеры и рендер [done]

Подготовка к нескольким камерам (например, руки игрока рисует вторая камера
поверх мира, чтобы они не проваливались в стены); самих рук здесь нет.

- У `Camera3D` есть **порядок** (меньше - рисуется раньше), **маска слоёв**,
  **режим очистки** (цвет и глубина, только глубина, ничего) и цвет **фона**
  для первого режима. Фон - свойство камеры, а не сцены: вторая камера,
  которая стирает цвет и глубину, берёт свой.
- `RenderSystem` хранит камеры сцены (камера добавляется сама, когда входит
  в сцену) и отдаёт те, у которых узел активен, по порядку. Данные кадра несут список видов вместо одной камеры; бэкенд рисует
  их по очереди, каждый со своей очисткой и только то, чей слой есть в его
  маске.
- **Главная камера** - первая по этому порядку, через неё видна игра:
  `scene.system<RenderSystem>()->mainCamera()`. Она нигде не хранится, ни в
  `Scene`, ни в файле сцены; чтобы сменить её, меняют порядок или
  выключают камеру. Камера, ушедшая из сцены, выпадает из списка сама.
- **Выбор главной камеры в редакторе**: инспектор камеры пишет "Главная
  камера" у главной и "Камера выключена" у камеры с выключенным узлом, у
  остальных - кнопка "Сделать главной". Она ставит камере order на единицу
  меньше, чем у главной (`orderToBecomeMain`), одним шагом с отменой.
  Флага "главная" рядом с порядком нет намеренно: два источника спорили бы
  (флаг у двух камер, ни у одной), а порядок по-прежнему решает, какая
  камера рисует поверх какой **[done]**.
- Своя камера редактора (игровой нет или игра не идёт) рисуется одним видом
  с фоном из темы редактора.
- **Превью камеры** в редакторе, как в Unity: пока камера выбрана, маленькое
  окно в углу окна вида показывает картинку через неё, чтобы ставить камеру
  на глаз. Кнопка на окне вида включает и выключает его, выбор - настройка
  редактора (`EditorSettings`, файл в папке пользователя) **[done]**.
- **Два окна во время Play**, как в Unity: "Игра" показывает главную камеру,
  "Сцена" остаётся со свободной камерой редактора, где узлы выбирают и меняют,
  пока игра идёт. Правки во время Play относятся к копии Play и пропадают
  после Stop **[done]**. На Play окно игры выходит вперёд и получает ввод; без
  игры оно показывает редактируемую сцену через её главную камеру. Положение
  мыши относительно окна игры появится вместе с HUD **[planned, step 8]**.

## Смена графического API [done]

API берётся из раздела Graphics настроек проекта (свой для каждой системы) и
меняется без перезапуска приложения. `Application` каждый кадр сверяет его с
работающим рендерером; при смене пересоздаёт только рендер:

```
onRendererLost      владельцы отпускают созданное через рендерер
                    (редактор: текстуры окон сцены)
UiLayer             отпускает отрисовку ImGui под старый API; контекст
                    ImGui, окна и раскладка остаются
Renderer            удаляется, пока жив его контекст
Window              пересоздаётся, только если новому API нужны другие
                    флаги окна (окна OpenGL и Vulkan в SDL разные)
Renderer            создаётся под новый API
UiLayer             отрисовка ImGui под новый API
```

- Сцена, проект, история правок и состояние редактора живут вне рендерера,
  который видит только снимок кадра, поэтому больше никто ничего не замечает.
- API, которого нет в этой сборке движка или который не дала система,
  оставляет прежний, с сообщением в логе, один раз.
- Vsync переключается у работающего рендерера, без пересоздания.
- Тем же путём рендер восстановится после потери устройства (Vulkan, D3D12),
  см. [этап RHI](#этап-rhi-planned-rhi) **[planned, RHI]**.
